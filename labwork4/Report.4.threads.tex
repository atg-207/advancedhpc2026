\section{Introduction}
In Labwork 4, we extend the RGB-to-grayscale conversion by migrating from a 1D grid layout to a 2-dimensional thread and block hierarchy. The goal is to preserve the native 2D spatial representation of images, evaluate the speedup gained across various 2D block shapes, examine hardware constraints, and solve classroom exercises on thread scheduling.

\section{Implementation}
Unlike the 1D flattened array approach used in Labwork 3, the image is passed directly in its 2D matrix shape $(H, W, 3)$:
\begin{itemize}
    \item \textbf{CPU Implementation}: Iterates sequentially through image height ($y$) and width ($x$) using nested loops to compute grayscale intensity:
    \[
    g = \lfloor(R + G + B) / 3\rfloor
    \]
    \item \textbf{GPU Implementation}: Implements a 2D CUDA kernel where each thread calculates its 2D global coordinate:
    \[
    x = \text{threadIdx.x} + \text{blockIdx.x} \times \text{blockDim.x}
    \]
    \[
    y = \text{threadIdx.y} + \text{blockIdx.y} \times \text{blockDim.y}
    \]
    A boundary check \texttt{if x < w and y < h} ensures threads beyond image borders do not perform invalid memory accesses.
\end{itemize}

\section{Experimental Results}

\section{Hardware Limit and Crash Analysis}
When attempting configurations such as $(64, 32)$ ($2048$ threads) or $(64, 64)$ ($4096$ threads), the kernel execution crashes with:
\[
\texttt{numba.cuda.cudadrv.driver.CudaAPIError: [1] CUDA\_ERROR\_INVALID\_VALUE}
\]
This crash occurs because NVIDIA GPU architecture strictly enforces a physical limit of \textbf{1024 threads per block} (\texttt{MAX\_THREADS\_PER\_BLOCK = 1024}). Any block launch requesting a total thread count exceeding 1024 is rejected at runtime by the CUDA driver.

\section{Discussion}
\begin{itemize}
    \item \textbf{Speedup}: The 2D CUDA implementation achieves massive acceleration, delivering up to $1393.5\times$ speedup over the sequential CPU baseline.
    \item \textbf{Occupancy \& Performance}: The $(4, 4)$ block ($16$ threads) yields lower performance ($0.20\text{ ms}$) because it is smaller than the hardware warp size ($32$ threads), leaving execution units underutilized. Peak efficiency is reached at $(32, 16)$ ($512$ threads, $0.15\text{ ms}$), achieving optimal warp scheduling and SM occupancy. At the hardware maximum $(32, 32)$ ($1024$ threads), latency slightly increases to $0.16\text{ ms}$ due to register pressure and block-scheduling overhead.
\end{itemize}
