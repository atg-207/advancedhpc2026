\section{Introduction}
In this labwork, we convert our previous 1D RGB-to-grayscale code into a 2D grid and block configuration. Instead of flattening the image into a 1D vector, we keep its native 2D matrix shape and observe how different block geometries affect running time. We also analyze hardware limits and answer the questions presented in the lecture slides.

\section{Implementation}
We measured the execution time of sequential CPU code against 1D and 2D CUDA kernels:
\begin{itemize}
    \item \textbf{CPU}: Loops sequentially over rows ($y$) and columns ($x$), computing grayscale pixel by pixel using $g = \lfloor(R + G + B) / 3\rfloor$.
    \item \textbf{1D CUDA}: Flattens the image into size $(N, 3)$ and computes the linear index:
    \[
    \text{tidx} = \text{threadIdx.x} + \text{blockIdx.x} \times \text{blockDim.x}
    \]
    \item \textbf{2D CUDA}: Keeps the original $(H, W, 3)$ shape and calculates pixel coordinates directly in 2D:
    \[
    x = \text{threadIdx.x} + \text{blockIdx.x} \times \text{blockDim.x}
    \]
    \[
    y = \text{threadIdx.y} + \text{blockIdx.y} \times \text{blockDim.y}
    \]
    A simple check \texttt{if x < w and y < h} ensures threads beyond the image boundaries do not write into memory.
\end{itemize}

\section{Discussion}
\begin{itemize}
    \item \textbf{1D vs 2D}: Both 1D and 2D grids achieve roughly the same execution time ($\approx 0.12 - 0.13\text{ ms}$). 1D has a slightly higher peak speedup because of simpler coordinate calculation, but 2D is much cleaner and more natural for working with images.
    \item \textbf{The $(4, 4)$ Bottleneck}: The $(4, 4)$ block performs noticeably worse ($0.19\text{ ms}$) because it only has 16 threads. As discussed in the slides, the GPU executes threads in warps of 32. Having fewer than 32 threads leaves half the warp inactive, wasting execution units.
    \item \textbf{Hardware Limits and Crash}: Testing configurations above 1024 threads (such as $(64, 32) = 2048$ threads or $>1024$ in 1D) causes an immediate \texttt{CUDA\_ERROR\_INVALID\_VALUE} crash. This directly reflects the hardware restriction shown in the slides, where a single thread block is capped at 1024 threads.
\end{itemize}

\section{Exercise Answers}
\begin{itemize}
    \item \textbf{Exercise 1 (Slide 24)}: The best configuration is \textbf{$16 \times 16$}. A $32 \times 32$ block has 1024 threads, exceeding the limit of 512 threads/block. An $8 \times 8$ block has 64 threads; with 8 blocks per SM, it only reaches $8 \times 64 = 512$ threads per SM (wasting half the 1024 limit). A $16 \times 16$ block has 256 threads, so 4 blocks fully populate the SM with $4 \times 256 = 1024$ threads.
    \item \textbf{Exercise 2 (Slide 25)}: The configuration that yields the most threads is \textbf{512 threads/block}. Since the SM can hold at most 4 blocks, $3 \times 512 = 1536$ threads, which fully reaches the 1,536 thread limit. Other choices either produce fewer threads (e.g., $4 \times 256 = 1024$) or cannot fit more than one block ($1 \times 1024 = 1024$).
    \item \textbf{Exercise 3 (Slide 26)}: The grid contains \textbf{2048 threads}. For a vector of size 2000 and 512 threads per block, we need $\lceil 2000 / 512 \rceil = 4$ blocks. This gives $4 \times 512 = 2048$ threads in total (where 48 threads remain idle due to boundary checks).
\end{itemize}
